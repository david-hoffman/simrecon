# Agentic Software Delivery System

**Version: 1.0** Git commits version edits; do not bump the release number while designing this system. This is the current specification, not installed software. Earlier conversation drafts are superseded, not released versions.

> One monorepo. Clarify material decisions. Select the route by risk. Preserve independent judgment and full checks. Record lessons and improve the instructions.

## 1. Keep the system small

Use an existing coding harness and four skills. Agents write all product/helper code and tests; the owner supplies intent and approvals, not engineering. Keep product code, tests, delivery instructions, and GitHub Actions in the same repository. Run one task per worktree; independent approved tasks may use separate worktrees. Use native harness sessions, Git commits, Markdown, and existing test tools; add only small launch scripts where necessary.

**Do not build a delivery platform:** no second repository, custom controller/state engine, GitHub App, external merge authority, permission broker, signed attestations, immutable evidence store, agent swarm, or tracing service. Fresh independent review sessions and ordinary CI remain where the selected route requires them; custom enforcement of role/file restrictions does not.

The owner accepts that “do not edit tests/workflows” and “append only” are prompt rules. Agents technically retain access. A workflow change, false report, or ignored instruction may defeat this process. GitHub checks only the configured CI, not whether agents obeyed these rules. Do not describe this design as tamper-proof or guaranteed to prevent bugs.

**Names:** the delivery system is the whole process; a coding harness runs an agent; a role is one session's responsibility; a skill is its procedure. No custom orchestrator is required.

**Normative language:** MUST is required behavior, not a claim of mechanical enforcement. This file defines policy and rationale; repository `AGENTS.md` is the single operational home for shared instructions. Skills contain role-specific procedures and refer to that home. Supporting prompts and generation templates must agree; they are not additional live rulebooks.

## 2. Setup and architecture intake

Start read-only. Inspect existing instructions, manifests, interfaces, tests, and documentation. Before proposing remediation, produce a small baseline inventory: existing failures, exact measured statement/branch coverage and its scope, environment/tooling problems, and unresolved behavior. Identify the revision, environment, and commands behind the evidence; label stale results. Use existing checks in a usable isolated environment, keeping generated reports temporary and leaving product/tooling files unchanged. If measurement is blocked, report it as unknown with the blocker and proposed measurement step. Do not run downloaded or repository setup scripts just to discover the project.

| Starting point | Route |
|---|---|
| Usable, owner-approved architecture exists | Reuse it. `docs/PROJECT.md` may simply link existing canonical documents. |
| Empty repository, no architecture | Interview the owner about the first useful outcome and constraints; propose a small architecture record. |
| Existing code, no usable architecture | Describe observed structure, ask what is intended, and resolve material gaps. Do not assume existing behavior is correct. |
| Architecture is unapproved, contradictory, or affected by this task | Reconcile only the affected decisions, then obtain approval. |

Architecture intake produces one short `docs/PROJECT.md`, using [the template](templates/PROJECT.md): purpose, constraints, stack, component responsibilities, public interfaces, verification commands, operation, approved gate mode and role/model-selection references. Prefer one deployable component. Markdown is sufficient; diagrams are optional. Link actual schemas instead of copying them. Architecture approval does not approve every future task.

Infer languages/frameworks from evidence in an existing monorepo. For an empty one, recommend a stack from the owner's requirements and obtain approval. Do not prescribe a product language because the coding harness uses it.

Choose current, coherent ecosystem tooling from primary documentation: one formatter, lint/static checks, native tests and coverage, dependency locking, and suitable security checks. Preserve sound existing choices. For example, a Python project might use Black plus Ruff linting and fast pre-commit hooks; this is an example, not a universal prescription. Repeat necessary checks in CI. Pin dependencies/actions appropriately; do not install competing tools.

Setup is the explicit exception that may create initial workflows and test infrastructure. Show the plan before applying it, separating delivery-tooling installation from existing-product remediation, with expected effort, measurement gaps, and required owner decisions for each. Installation approval does not approve product repairs or settle numerical behavior. In a repository without a commit, an authorized metadata-only initial commit may establish `main`; do not put an untested application there. A minimal callable scaffold may support the first tests, but label missing-feature evidence honestly.

Before expensive dependent work, check actual interpreter/platform and lock identity, installation/import health, and isolated/nested environment creation where required. Reuse applicable environment evidence only while recorded inputs and current health hold. Check reviewer launch/authentication/connectivity only when independent review is required and capability evidence is missing or stale; use an observed valid launch or the smallest necessary probe, not a redundant reviewer session. Stop dependent phases on prerequisite failure, retain unaffected evidence, and diagnose before an authorized retry.

Repeating setup inspects and completes approved gaps; it does not overwrite working conventions. Missing architecture prevents A or product implementation, but not read-only discovery or approved setup. Retain the 100% requirement. The owner chooses how to bring an existing project into the system case by case; this specification prescribes no automatic remediation sequence. Expose substantial baseline maintenance, missing contracts, and dependencies that would prevent a proposed task from passing full verification before approving that work. Installed tooling does not make a failing/under-covered product ready.

## 3. Step 0: clarify and approve each task

Use the same `intake` skill for architecture and tasks. Check the architecture route above and reuse settled answers. Ask only about material ambiguity in behavior, scope, interfaces, permissions, data, errors, cost or acceptance, usually at most three questions per turn. Recommend concrete defaults; silence is never approval. Internal implementation choices can remain delegated.

Create one task document from [the template](templates/TASK.md). Capture observable requirements with stable IDs, non-goals, public interfaces, positive/error/boundary examples, named edit ownership, checks, risk route, gate mode, escalation triggers, role/model/effort choices and preparation/execution budget. Expected results must follow approved behavior, an applicable primary reference or a mathematical invariant. Unspecified units, conventions and estimator choices return to intake; coverage does not choose semantics. References must apply to the approved interface. For bugs, separate observed behavior, expected behavior, reproduction and root-cause hypotheses. A bounded investigation may be approved to report an uncertain cause; it does not authorize a speculative repair.

Before tests, inventory normal operation, invalid input, representation limits, operation-time failure, external compatibility and documentation. Identify paired permitted inputs where a rejection could accidentally narrow the contract. This is an inventory of obligations, not a requirement to invent behavior or six scenarios for every task.

For a large request, create a slice plan at `docs/tasks/<plan-id>.md`, linking each contract, observable outcome, dependencies, budget and completion condition. Each slice has one checkpoint lineage and candidate PR. Independent contracts may use separate worktrees; dependent slices wait for completed prerequisites in their baseline. Each intended baseline must support full verification and global coverage. Expose infeasible baseline gaps for an owner adoption decision before promising a sequence that cannot finish.

Default to at most **five behavioral scenarios per slice**; explicitly approve a larger coherent contract once. A scenario is a distinct approved decision and observable outcome. A distinct rejection rule, interpretation, output guarantee or boundary outcome is another scenario. Equivalent values exercising the same decision are coverage examples, which may be mapped under that scenario. Test functions, parameter counts and branches do not determine scope. Do not group unrelated contexts to evade the limit. Additional equivalent values need no new approval while meaning and budget remain unchanged; new meaning returns to intake. The test author maps scenarios/examples to tests; the required independent reviewer checks that mapping.

For mechanical and bounded work, a complete explicit owner request may itself authorize the named scope, route, checks and inherited constraints. Record the actual instruction and send a concise read-back; do not demand a second yes merely because the record was written afterward. A missing material answer or new budget still needs an answer. High-risk work and delivery-policy amendments retain explicit approval of the identified proposal. Present a slice plan and all its contracts together for one approval, identifying the documents/revision in conversation or GitHub discussion. Do not fabricate approval or infer it from silence.

Approval authorizes routine execution within the recorded scope: named role launches, authorized checks, in-scope repairs within remaining allowances and unchanged-scenario redistribution. No repeated approval is needed for those transitions. Renew approval for changed behavior/interfaces/permissions/data sharing, tier downgrade, budget extension or exhausted repair allowance. Architecture approval does not approve scientific features. Unchanged-scenario redistribution preserves interfaces, dependencies, permissions, total budget and consumed allowances; record the mapping. Other material changes renew affected tests/reviews.

Intake drafts examples, not executable tests. High-risk A/B receive only approved behavior/public interfaces, approved fixtures, expectation sources and test conventions. Exclude interview/coordinator transcripts, patches, implementation hypotheses, implementation-bearing Current state, coverage maps and existing lessons; sanitize correction findings and attachments to the same boundary.

## 4. Delivery routes and fresh independent sessions

Select and record the route before execution. Behavioral impact and uncertainty decide; changed-line count does not. A mixed task takes the highest route unless independently scoped contracts justify a split. Uncertainty promotes the route. Data-loss behavior is high risk even for a settled overwrite/truncation repair; conventional expectations and a small diff do not make it bounded. Failure category and risk are separate: a network failure does not lower risk, and a lower-route failure does not authorize scientific/interface repairs.

| Route | Eligibility | Ownership and acceptance |
|---|---|---|
| **Mechanical** | Non-normative prose, links, formatting or deterministic edits; no executable behavior, dependency, gate, permission or policy change | One worker checks a reviewable diff and relevant deterministic checks. Owner acceptance; independent review only when the contract requires it. |
| **Bounded** | Established conventional behavior or explicitly scoped dependency/platform/lint/check maintenance with understood impact; no scientific/binary meaning, new custom oracle, risk of data loss, security/permission boundary or unresolved interface | One worker may inspect implementation and author the named tests/fixtures and maintenance files. One fresh reviewer independently checks expectations, product and infrastructure behavior, preserved gates, scope and exact passing candidate. The worker never approves its own repair. |
| **High risk** | Scientific/numerical semantics, binary representation, custom oracles, data-loss behavior, security/execution permissions, substantial interfaces, unresolved semantics or uncertain impact | Fresh blind A, fresh blind B, C and fresh D. Reviewed tests remain frozen for C. |
| **Policy documentation** | Delivery-policy amendment or adoption | Explicit owner approval of the identified policy scope plus fresh independent policy review before activation. Documentation author may change only named policy/instructions; no fabricated product-red evidence or scientific A/B suite. This is not self-classified mechanical work. |

Dependency/workflow/gate maintenance always requires independent review and explicit edit scope. Changed execution authority/security boundaries use high risk. Removing tests/assertions requires a reviewed obligation mapping; promote uncertain impact. Coverage, discovery, fixtures and delivery rules have named ownership and authorization. No route permits weakening gates or using maintenance authority to bypass a defect. A bounded worker is a separate packet/mode, never high-risk C with renamed restrictions.

### High-risk roles

| Role | Completion | Restrictions |
|---|---|---|
| **A: test author** | Behavior tests, scenario/example mapping, independently justified expectations/tolerances and classified baseline evidence, or a contract blocker | No implementation, its history/conversations, implementation-bearing state or existing lessons. |
| **B: test reviewer** | Accept an exact test/fixture revision or report evidenced defects/gaps, independently recalculating the oracle | A's blind inputs plus exact tests and sanitized evidence; report only. |
| **C: implementer** | Smallest necessary product change, possibly none, and passing candidate/check results, or classified blocker | No reviewed tests/fixtures/snapshots, discovery/coverage settings, workflows, skills/delivery rules or unrelated interfaces. |
| **D: final reviewer** | Accept the exact passing candidate or return correctness/security/scope/simplicity findings | No repair and self-approval; no inherited implementation conversation. |

Initial high-risk A/B/C/D use fresh native root sessions; B/D correction verdicts remain fresh. Bounded and policy reviewers use fresh independent sessions with no author/implementation history; a native launch is an available method, not extra mandatory infrastructure. No reviewer forks or inherits the author/implementation conversation. Disable optional memory/delegation where supported. The coordinator launches roles; the packet says the recipient is already the fresh root and does not launch another role. A may continue its own author session for approved corrections while blindness holds; C may continue its own session for an authorized repair. Fresh B/D verdict sessions remain mandatory. Exposure, changed scope or excessive context warrants a fresh permitted author; clearing context or rerunning clean diagnostics never restores an exposed blind session. Continuation renews no scope, budget, rounds or repairs.

Give each role a narrow [public](templates/PUBLIC-PACKET.md) or [candidate](templates/CANDIDATE-PACKET.md) packet: approved scenarios/contract, route/mode, permitted inputs and named edit ownership, relevant revision/base/checkpoint, exact checks, model/effort, output/completion, budget and remaining allowances. Do not cycle roles per assertion or uncovered line. Reports contain verdict/findings, scope, commands/results and evidence links; link unchanged mappings/environment records. A fresh coordinator may take a [compact handoff](templates/HANDOFF.md) at a phase boundary when completed context dominates; replacing context renews nothing.

Before A/B imports/probes/tests, arrange source-free warning, traceback and relevant subprocess rendering while retaining categories/messages, locations, failure counts and status. Pytest `--tb=no` alone does not remove warning source. Disclose accidental exposure and route replacement; no custom filesystem isolation is claimed.

A **test oracle** decides correctness. B and bounded reviewers assess that logic, not syntax alone. Independently derive expectations from the contract; challenge parsers/observers, units, profile assumptions, tolerances, legitimate alternatives, permitted positive inputs and plausible wrong results. Do not repair malformed product output in an oracle or invent unspecified priorities. Use the required review; no extra mandatory reviewer or mutation platform.

After two B nonacceptances, B diagnoses the blocker before another A rewrite. Clarify specific ambiguity through intake or propose genuine split points. Restart only under section 9's documented resolution/extension rule. An automatic model escalation or invented ambiguity is no diagnosis.

Accepted existing-code tests may pass initially. Do not manufacture red, mutate product or require unnecessary implementation. Product-red evidence requires a valid test reaching the intended approved behavior and failing for its approved reason; scaffold feature absence is not reproduction of an old bug. Classify before repair; uncertain/mixed causes need bounded diagnosis and separate records. Classification grants no edit authority.

| Failure category | Routing and checkpoint |
|---|---|
| Environment/tooling | Authorized setup/maintenance diagnosis; stop dependent phases, then resume and rerun affected checks. Setup/import failure alone is no product defect. Unchanged tests retain their checkpoint; changed tests/fixtures need independent review. |
| Test defect | High-risk A corrects permitted tests and fresh blind B reviews the delta/dependents below; C never edits tests. Bounded worker corrects named tests, then fresh independent review. Record revised checkpoint and valid baseline evidence. |
| Product defect | Approved valid evidence routes to C or the bounded worker within remaining allowance, then passing checks and fresh required final review. Unchanged tests retain their checkpoint. |
| Unresolved requirement | Intake resolves/obtains approval; renew affected tests/reviews before implementation. Coverage pressure supplies no approval. |

A failure to follow an existing instruction is execution error, not automatically an instruction gap or new repair scope.

### Scoped correction review

For high-risk corrections, provide A/B the prior accepted checkpoint, approved public contract, sanitized public reproduction/finding, changed tests and a dependency mapping derived only from tests and approved requirements. Translate implementation discoveries into public behavior; new meaning returns to intake. Exclude C's conversation/implementation, coverage-line maps, implementation-derived explanations and raw D reports that expose them. Unchanged accepted portions may retain evidence.

Fresh B may accept a revised checkpoint after reviewing the changed oracle/tests and every dependent case only when retained portions are unaffected and their prior evidence still applies. A shared parser, observer, fixture, tolerance, schema or expectation change expands review scope. A changed public meaning first needs approval; changed meaning or inadequate dependency mapping requires a fresh complete review of affected behavior. B may expand scope; A cannot declare its own delta safe. Changed high-risk tests retain A/B acceptance before C. Tests added after implementation are supplemental; a revised checkpoint cannot recreate original test-first evidence. Each completed correction review counts in its recorded window; preserve all earlier windows and spending. Lower-route corrections retain the independent review their route requires.

Commit the accepted tests and identify the **test checkpoint**, frozen by convention. Bounded workers may create a reviewed test/candidate checkpoint together under explicit test ownership. A branch without an open PR may back up a failing checkpoint when labeled incomplete; backup is never readiness. Publication permission still comes from the task.

### Candidate gate and acceptance

Run cheap applicable checks before expensive tests. **Default: the responsible worker runs canonical full local verification for the exact candidate before opening/reopening a PR (draft included) or pushing to an open PR. Any known failure, including incomplete coverage, blocks submission.** Record candidate/tree, command, environment/inputs/base and exact result; confirm tracked bytes match the commit and remain unchanged. A changed candidate needs a new full run. Closing/moving a PR does not waive the gate. CI repeats all required platforms. The conditional alternative in section 6 requires separate approval and proved prerequisites; it is never inferred from a green PR.

Do not spend final acceptance review on a known failing candidate. Required reviewers assess meaningful tests/oracles, real behavior, evidence validity, restricted-file compliance and simplicity. D forms its independent assessment before consulting current-task implementation lessons. Applicable passing evidence need not be duplicated just to obtain the same verdict. A violation routes to the coordinator; restore the intended baseline before continuing.

Keep one concise **Current state** in the task or a linked PR/discussion: approvals, route/gate, candidate, checkpoint, review/check references, classified blockers, next action and compact metrics with evidence links. Final candidate identity/results belong outside its tracked tree in conversation/PR; prepare that pointer before verification. Do not edit verified bytes to record their own hash. Replace superseded status; Git preserves history. Only lesson entries are append-only. No competing state store or mandatory trailers.

After full required CI and independent acceptance where required, present the PR for the owner's normal merge action. Further changes renew affected checks/review. Merge and release remain explicit owner actions; release also follows project smoke/recovery instructions.

## 5. End-to-end first, not end-to-end only

**Coverage is primarily earned by exercising useful behavior through the real entry point.** For a web app, run important browser journeys through the real application/backend and a disposable test database. For a CLI, run its executable and inspect outputs, exit codes, and files. For a service or library, use its public API and observable effects; do not invent a browser layer.

For each changed requirement, start with the smallest realistic success, failure, and boundary scenarios. Map equivalent coverage examples under the same approved decision; a new rejection, interpretation or output guarantee is a distinct scenario and needs approval. Coverage remains a separate measured gate, not evidence that all permitted behavior was specified. Assert the outcome, not merely that a mock was called, a file contains a string, or the application compiles. Trace expected results to the contract/reference/invariant required by section 3, never the implementation being tested. Contract-supported invariants may test part of a behavior while an absolute interpretation remains unresolved; record that limit rather than claiming full behavioral validation. Do not duplicate every end-to-end assertion with unit tests. These choices borrow pstack's [behavior](REFERENCES.md#r2--test-behavior-not-implementation) and [real-artifact](REFERENCES.md#r3--verify-the-real-artifact) emphasis, and, for browser projects, [Playwright's user-visible testing guidance](REFERENCES.md#r8--end-to-end-testing-practice).

Use integration or unit tests for a genuine gap: difficult error injection, combinatorial logic, or a branch that would make a whole-system test slow or brittle. No unit-test quota or fixed test-type percentage. Do not forbid valid negative assertions or property tests just because a heuristic dislikes them.

A behavioral test is implementation-coupled when a refactor preserving its approved observable contract would break the test. Test interfaces that production code or real callers also need; do not require production exports, wrappers, or injection hooks solely for tests. D investigates code referenced only by tests, while recognizing that a public library API may serve external callers. An explicit public, platform, or architectural contract can justify a structural check; suspicion alone is not authority to delete an existing test. These judgment criteria adapt [OpenClaw's test audit](REFERENCES.md#r10--openclaw-test-audit), not its implementation-reading workflow.

B or the bounded reviewer rejects execution solely to raise coverage without a meaningful correctness check; negative tests passing because an unrelated validation rejected the input; fixtures that supply the result whose production behavior is supposedly tested; and test names claiming more than their inputs exercise. A check need not use a literal assertion statement: an expected exception or successful completion may itself be approved observable behavior. Require the intended path and outcome, not a particular assertion syntax.

The authorized test author chooses and explains numerical tolerances from the approved algorithm description, applicable references, conditioning/error bounds, and arithmetic precision available in the blind packet. Identify absolute/relative comparisons and relevant scales. The independent reviewer checks both that legitimate numerical variation passes and that plausible wrong values fail. Do not inspect implementation to derive tolerances, tune them to candidate output, or relax an explicit accuracy contract. Missing behavior still returns to intake; choosing a justified test tolerance does not itself require a new owner accuracy specification.

Test owned components together where practical. Stub uncontrollable external services at their boundary, document what is not exercised, and use an approved provider sandbox check where integration correctness requires it. Do not mock the internal path whose behavior is the requirement. Use synthetic data, isolated state, readiness checks rather than fixed sleeps, and bounded waits. A suite that fails and then passes on retry still needs investigation; do not hide flakiness.

Keep the original **100% measured statement and branch coverage** requirement across instrumentable owned runtime code, globally and per package, from the combined suite. Instrument relevant subprocesses, servers, and browser code; a passing browser test alone does not measure backend coverage. Include never-imported files. Inspect exact metrics, not rounded display values.

Narrow documented exclusions may cover vendor, generated, or non-executable files—not inconvenient handwritten branches. Missing/unsupported coverage is a reported gap, never fabricated success. Do not reduce the threshold through `doctor`. Complete measured coverage is not proof of complete behavior. Use existing tools and the test review; no mandatory mutation-testing platform.

## 6. Ordinary GitHub CI

Use the monorepo's ordinary GitHub Actions workflow. Prefer one required job, `verify`, running the project's canonical checks in order. A genuine multi-platform need may require several jobs; keep every required result visible. No custom gate publisher or GitHub App.

By default apply section 4's exact-candidate full local verification condition at PR submission, including updates to an open PR. A separately approved eligible CI-authoritative pilot must satisfy every prerequisite below; unknown evidence retains the local gate. Fast local hooks may provide formatting/lint feedback on all commits or pushes; invoke the full command for submission. A blanket full pre-push gate must not prevent permitted pre-PR backups. No custom PR-state controller is required; hooks are bypassable feedback. CI repeats the shared command on the submitted commit and its supported platform matrix; local success does not certify other platforms. Report failures from any backup CI honestly. Newly discovered failures return through section 4's routing before submission.

CI should install locked dependencies, run formatting/lint/types as applicable, build, run tests/coverage, and retain useful failure reports. Fail on failed commands, empty test discovery, unexpected skipped/focused tests, and missing required reports using native tools where available. Do not use `continue-on-error` or path filters that silently remove required validation. Keep diagnostic output short with access to full logs.

Configure native protection for the approved PR target branch (normally `main`): PRs, required CI, current branches, and no ordinary force-push/deletion or bypass. [GitHub setup](GITHUB-SETUP.md) explains the owner actions and capability limits. GitHub accepts some skipped/neutral check conclusions, so a required job should actually run, not be conditionally skipped ([source](REFERENCES.md#r7--github-protected-branches)).

**Workflow/test editing restrictions are prompts, not engineering.** Setup or a bounded worker with explicit named maintenance ownership may change infrastructure; high-risk C may not. A/B own high-risk test changes; the bounded worker may own the named tests, always with fresh independent review. CI executes repository-controlled files and cannot independently prove those restrictions were respected. There is no anti-tampering certification.

Use ordinary CI secret hygiene: no production secrets in test runs, no secrets committed, and only necessary token permissions. A local hook is feedback, not a substitute for required CI.

### Conditional CI-authoritative submission

This alternative is eligible only after a separately approved, bounded evaluation of duplicate full-run cost and native protection/check/base/artifact prerequisites. It is unavailable for high risk or uncertain evidence. Start with settled bounded work already requiring independent review; adding mechanical work needs explicit approval of the extra review. Initially exclude changes to this alternative's gate, workflow/discovery/coverage/protection, build/release proof or execution authority.

Verify effective target protections/rulesets, trusted check sources, base/integration requirements and bypass settings read-only. The approved gate configuration must name the complete expected platform/job/shard/report set and accepted CI event/ref. One ordinary required aggregate must verify that set for the final named head/base/integration state and fail for failed, cancelled, skipped, neutral, absent or incomplete results. A green aggregate or PR alone proves neither completeness nor enforcement; unknown/ineffective controls block eligibility. Configure protections only through authorized setup. Native controls do not enforce role blindness/file ownership.

Record exact suite-tested revision, corresponding head/base, platform/environment, complete owned coverage per platform/package, artifact digest, resolved version and relevant build/version inputs. PR head, synthetic integration and final merge/squash/rebase can differ. Source-tree equality alone cannot prove a Git-derived artifact/version. If the integration strategy cannot supply the required exact candidate/artifact proof before merge, defer eligibility instead of inventing a release process. Changes to candidate/base/tests/dependencies/checks/environment/version inputs invalidate affected results and acceptance.

The approved focused local gate must pass before opening/updating the PR; unexecuted full local verification is the only exception. Known applicable failures still block submission until classified repair and relevant local checks establish their cause is addressed. A PR awaiting full CI is unverified and never ready. CI failures stop readiness and route within existing allowances; updates repeat the focused gate and renewed full CI. Final independent acceptance follows all required full CI on the final candidate. Worker readiness, reviewer verdict, native checks, owner merge and release are distinct. Failure or lapsed prerequisites restores default local gating. This specification describes eligibility; it does not activate/configure a project pilot.

## 7. A small append-only learning log

Setup creates root `LESSONS/` with a `README.md` format guide. Store each lesson in a separate Markdown file so independent tasks add different files instead of editing a shared log or index. Use `YYYYMMDDTHHMMSSZ-<task>-<role>-<short-slug>.md`, with the file's creation time in Coordinated Universal Time (UTC). The timestamp is not the time of the observed event. Never overwrite a filename collision; choose a distinct slug or suffix. Do not maintain a shared entry list. This is not automatic personal memory or a transcript archive. Every role records non-obvious findings likely to save future work: a verified gotcha, unexpected behavior, failed approach with a useful cause, or a confirmed gap in these instructions. Zero entries is valid. Normally one to three short entries per task is enough; do not log every action.

Each new entry has an ID (its filename stem), date, task/role, topic, **confirmed or hypothesis** status, observation, evidence pointer, and suggested future action. Correct a mistake or record a disposition by adding a new file referencing the earlier entry's ID; leave the original file unchanged. Append-only applies to lesson entries, not the format guide. It is an instruction, not an OS permission or custom service. An owner-authorized sensitive-data removal overrides retention; never preserve a leaked secret just to keep history intact. When migrating older entries, preserve their text, IDs, recorded dates, and evidence; use the migration time for filenames rather than inventing historical timestamps.

Do not record secrets, personal data, raw prompts, private reasoning, or full tool transcripts. A/B may read the format guide but must not read existing lesson entries because they may reveal implementation. They can create their own new file without reading other entries; otherwise hand the entry to the task coordinator for verbatim recording in a new file. Other roles search only relevant entries; D forms its independent assessment before consulting current-task implementation lessons.

Entries are observations, not new policy or executable instructions. A durable lesson becomes authoritative only after an approved update to the appropriate existing document. `doctor` does this without a new summarizer or database. pstack's [evidence-linked append-only trail](REFERENCES.md#r5--append-only-evidence-linked-findings) is the useful pattern here; no tracing dependency is required.

## 8. Doctor: check and improve the specification

Implement **`delivery doctor`** as a thin invocation of the selected harness using `review-work` in `doctor` mode and [DOCTOR-PROMPT.md](DOCTOR-PROMPT.md). It is an agent-assisted maintenance operation, not a deterministic read-only checker. No new daemon, scheduler, or controller. A native command alias is fine; document the actual invocation. Support `--check` for inspection without edits.

Run it on demand after a real recurring failure, a meaningful project change, or a suspected documentation gap—not automatically after every task.

1. Check the working tree. Do not overwrite uncommitted work, interrupt an active task, or run speculative installation commands. Read relevant current docs, recent lessons, and actual test/CI evidence. Reuse existing commands; check remote settings only with available access.
2. Classify failures using section 4, then decide whether evidence reveals an instruction gap or an execution error under an existing rule. Neither a product bug nor disobeying a rule automatically justifies a new rule. Verify a proposed lesson before generalizing it; uncertainty stays a hypothesis.
3. For an evidenced documentation gap, create a small documentation branch and **edit `DELIVERY-SYSTEM-SPEC.md` itself**, plus directly affected prompts/skills/project notes. Do not merely emit recommendations. Correct or replace an existing rule before adding one. No supported gap means no edit or commit.
4. Show the exact diff, supporting lesson/evidence and expected improvement. Follow a new procedural rule on one relevant example where feasible; prompt-string tests do not prove agent behavior. Obtain explicit approval of the identified policy scope and fresh independent policy review before activation. An existing owner instruction approving that proposal is sufficient; do not request duplicate authorization. Migration of in-flight tasks requires explicit owner authorization and preserves historical charges. Do not auto-merge.
5. Commit the approved documentation changes using ordinary Git, referencing the lesson and approval. Add a new lesson file recording a disposition such as “addressed by commit …” and the earlier entry's ID; do not rewrite its original entry.

All package documentation remains **Version 1.0**. Git commits/PRs supply revision history and rollback. Do not create numbered copies of the specification, invent releases, or put a commit's own hash inside the bytes it identifies. Runtime dependencies retain their real versions.

Doctor must not rewrite tests/workflows/runtime code, lower acceptance thresholds, remove an inconvenient requirement, or bless architecture drift merely to make the current result pass. Those findings become scoped, owner-approved tasks. Material product/architecture questions return to intake. Diagnostic docs edits are the explicit exception to ordinary workers' “do not edit the spec” rule; the limits are still instructions, not enforced permissions.

## 9. Cost and completion

One active task per worktree. Use the approved mechanical, bounded or high-risk route, or separate policy-documentation scope. Default high-risk A/B allowance is two completed B reviews per window; acceptance closes it. A later evidenced authorized correction opens a recorded window with its reason, retained checkpoint evidence and prior windows. Completed delta reviews count as rounds. A new session, renamed task or resubmission alone opens no window.

After two nonacceptances stop rewrites for B's diagnosis. Restart only when B confirms approved clarification or a genuine split resolved the diagnosed ambiguity/scope problem, or the owner explicitly extends/disposes of it. Record the resolution and prior rounds. Replacing a checkpoint or escalating a model is no resolution.

Default high-risk C allowance is one corrective implementation cycle after initial C. Bounded work also defaults to one corrective worker cycle after initial work unless the contract says otherwise; record its own review/repair allowance explicitly. Mechanical/policy scopes use their approved allowance, never a borrowed C reset. Further repairs need explicit extension. Splits allocate remaining budget/repairs across children, never multiply them. Planned independent new slices are distinct work; relabeled corrections are not. Charge preparation, calibration, diagnosis, failed launches/checks, environment/test correction, reviews and rework in the approved budget unit. Record owner effort in its stated units without redefining that budget. Context/session replacement and migration preserve all spending. Stop at the approved unit/hard limit; missing metering is unknown, not a guaranteed financial cap.
