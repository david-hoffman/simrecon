# Proposed pristine library design

**Version 1.0** Git versions revisions. Approval pending. [PROJECT.md](../PROJECT.md) is the canonical project decision record; this document supplies its design detail.

[UML data flow](data-flow.md) shows how these responsibilities exchange data, with file access separated from pure functions.


Recommend a functional Python library using NumPy arrays and small explicit metadata records, with bounded file access. Retain SciPy for later approved numerical operations. Use the existing Python 3.13/uv scaffold and macOS/Linux checks initially; broadening Python/platform support is a separate packaging decision. [The intake comparison](../tasks/architecture-intake.md#design-comparison) also considers xarray/Dask and a compiled core with Python bindings.

The public boundary has four operations: `inspect` reads metadata without loading pixels; `read` loads a selected block; `harmonize` resolves metadata/layout for file or caller-provided arrays; `write` saves a block or streams a described source. These are responsibilities, not approved signatures. The command-line interface (CLI) is a thin front end to the same functions, initially exposing inspection and conversion with explicit selection/profile/metadata options. Library and CLI must share validation and errors. Future reconstruction functions receive image blocks, calibration, and operation-specific parameters explicitly.

Use two small value records: `DatasetInfo` describes source, data kind, named axes, dimensions, stored dtype, sampling, acquisition metadata, provenance, and unresolved fields; `DataBlock` holds a selected NumPy array and its corresponding metadata/index selection. Descriptors carry no open file handles and do not cache processing state. Parameters are separate operation-specific records, not an image object's changing settings. Pure metadata/numerical functions return results and do not mutate caller-owned arrays. File reads/writes and scoped resource lifetimes form the explicit side-effect boundary. Internal scratch buffers may be reused within a call; frozen metadata does not make NumPy storage deeply immutable.

Model acquisition axes by name (`time`, `channel`, `orientation`, `phase`, `z`, `y`, `x`) and explicit source layout. Counts are data, not fixed constants. Preserve incomplete/irregular acquisitions as explicit mappings or unresolved information; do not silently invent a rectangular acquisition. A raw block selected for one channel/time point can have `(orientation, phase, z, y, x)` axes; reconstructed images use spatial axes. Do not impose all acquisition axes on every image. An optical transfer function (OTF) is a distinct frequency-domain data kind with order/frequency axes, radial-versus-Cartesian layout, and its own sampling metadata. It cannot be passed as a spatial image merely because both came from MRC.

Harmonization combines file metadata with explicit user overrides, records old/new values and their sources, and checks the resolved layout against the actual payload. Unknown acquisition ordering or extended-header schema requires an explicit profile/override before harmonization. Inspection may report unknown fields. Overrides cannot make a truncated payload or an impossible dimension product valid. Normalize spatial units to micrometres, wavelength to nanometres, phase to radians, and frequency sampling to reciprocal micrometres when source semantics establish the conversion. Retain original values/units; unknown timestamp/dose/drift units stay unknown until a contract settles them. No background correction, rescaling, calibration estimation, or reconstruction occurs during harmonization.

Keep a few components under `src/simrecon/`: model/metadata resolution; input/output adapters (initially explicit legacy and modern MRC dialects); later numerical operations/calibration/estimation; and the thin CLI. Adapter dispatch stays private and simple. Add another adapter when a concrete source requires it; introduce no plugin registry, scheduler, generic backend framework, or native kernel in the first slice.

Modern MRC output uses a standard main header/data block plus a versioned documented extended-metadata schema in the same file. Propose UTF-8 JSON metadata containing data kind, logical shape/axis order, source-plane mapping, units, acquisition information, and override provenance. Use a compact factored mapping where possible, with explicit exceptions for irregular data. The exact extension tag, length/framing, metadata limits, supported dtypes, and header mapping need approved format contracts. A project-specific tag must not be represented as officially registered. Preserve meaningful source metadata and uninterpreted extensions with their provenance rather than assigning them invented units. Unknown metadata can be preserved without being used numerically.

Use the maintained `mrcfile` package as the candidate for modern MRC writing/reading, subject to an approved contract and compatibility evidence. Legacy Priism handling is a separate decoder boundary: use an applicable maintained decoder only if its semantics match the selected dialect; otherwise independently author the bounded codec from documented format behavior and independent fixtures. No IVE/Priism import, linking, executable wrapping, or copied source. Frequency-domain metadata belongs in the extended schema, not falsely labeled spatial MRC cell dimensions.

ImageJ's desired view is five-dimensional: X/Y/Z/channel/time. The owner accepts currently supported MRC behavior initially, with a better solution later. Preserve all acquisition axes in the library and the self-contained metadata, but distinguish file preservation from viewer interpretation. Bio-Formats documents base-MRC support with limited vendor-extension handling. Its inspected `develop` MRC reader gives ordinary non-RGB data one channel/one time point and skips the extended header. This is primary source evidence, not a test of the owner's installed reader. First MRC contracts must pin the relevant ImageJ/Bio-Formats path and establish supported pixels, orientation, scale, dimensions, and declared limitations with asymmetric fixtures. Do not report a flattened stack as correct channel/time/Z interpretation. Raw SIM additionally has phase/orientation axes; displaying them in a five-dimensional viewer requires an explicit mapping or selection, never silent relabeling. [Format support](https://bio-formats.readthedocs.io/en/stable/formats/mrc.html), [reader source inspected September 30, 2026](https://github.com/ome/bioformats/blob/develop/components/formats-gpl/src/loci/formats/in/MRCReader.java).

A later OME-BigTIFF adapter or MRC reader integration can address complete ImageJ X/Y/Z/channel/time interpretation without changing the numerical core. OME-TIFF explicitly represents channel/time/Z ordering, and Bio-Formats provides a reader; this makes it a candidate, not verified performance or compatibility for this project. Large-file export and correct ImageJ interpretation need their own approved contract and evidence. No new format or ImageJ plugin is implemented or approved by this intake. [OME-TIFF specification](https://ome-model.readthedocs.io/en/stable/ome-tiff/specification.html), [Bio-Formats OME-TIFF support](https://bio-formats.readthedocs.io/en/stable/formats/ome-tiff.html).

The scale example is `2048 × 2048 × 40 × 3 × 5 × 5 × 100`, provisionally interpreted as X/Y/Z/orientation/phase/channel/time. It has `1,258,291,200,000` pixels: `2.2888 TiB` at uint16 or `4.5776 TiB` at float32 (`1 TiB = 2^40 bytes`). One channel/time-point raw acquisition at float32 is `10,066,329,600 bytes = 9.375 GiB` (`1 GiB = 2^30 bytes`); multiplying by five channels and 100 time points recovers the full size. These are storage calculations, not a measured runtime or peak-memory promise. RAM and latency targets remain unspecified.

Design inspection and conversion for selected reads and bounded block writes from the first slice. Use plane/range access with deterministic scoped file lifetimes; no whole-file materialization or full acquisition copy is required. The owner's fallback 3D processing unit is one channel/time point's complete Z acquisition across required phases/orientations. Future scientific contracts determine in-memory working sets, scratch staging, Fourier transform scope, and any valid subvolume subdivision. Chunked input/output alone does not make a whole-volume numerical transform bounded-memory. Use explicit memory/worker choices and assess selected-block peak memory; do not promise throughput without benchmarks. [NumPy memory access](https://numpy.org/doc/stable/reference/generated/numpy.memmap.html), [SciPy transform controls](https://docs.scipy.org/doc/scipy/reference/generated/scipy.fft.fftn.html).

This proposal selects responsibilities and representations for approval. Exact signatures, supported legacy variants/byte orders/modes, numerical conventions, output metadata schema, memory/error contracts, and independent fixtures must enter approved slices before executable tests or implementation. Keeping small function boundaries leaves room for a later xarray bridge, chunked store, GPU backend, or profiled native kernel; none is part of this first delivery or a promise of drop-in compatibility.
