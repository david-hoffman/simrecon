## Concrete expensive path: sparse MRC extension rejection

`tests/test_mrc_conversion_coverage.py:168` (`M41`) writes a genuine sparse file with extension length **2,147,483,647 bytes**, confirms sparse allocation, inspects and harmonizes it, then requires `header_unrepresentable` when writing modern MRC. This is a real representation-boundary proof. It must remain. `src/simrecon/_modern.py:write` currently opens a destination, calls `stage_metadata`, and only afterward computes the padded HDF5 size and calls `header`. `stage_metadata` copies the complete opaque source extension into a real HDF5 dataset in1MiB chunks. The final HDF5 carrier necessarily exceeds its signed32 NSYMBT field, but the present path can first materialize/copy approximately2GiB of opaque data. The sparse source is cheap; the staging path is not necessarily cheap.

This is directly established control flow, not a runtime estimate. Inspect coordinator baseline timing/I/O/disk evidence before spending on it. A cheap rejection of a provably impossible extension before staging could eliminate wasted work while preserving the exact public code and byte contract, but it edits the binary writer and changes operation/destination timing. It therefore needs named production ownership and the required high-risk route; this lane grants none. Do not simulate the result by mocking `stage_metadata`, shrinking the extension below the representation boundary, replacing the public write with a private header call, or deleting M41. None is a stronger keeper for its current independent sparse-file/public-write obligation.

The MRC range witnesses are distinct: M26 overflow, M40 underflow and M41 extension-carrier bound. They cannot substitute for one another. M41 currently permits a partial new destination because a later failure may leave one; do not invent an unsupported existing-output cleanup/atomicity guarantee while optimizing.

## Retained false positives and limits

* M45/M46 noncanonical decimal keys are deliberately valid for MRC harmonize and deliberately invalid for raw declaration's canonical-decimal schema. Sharing a normalization oracle between them would violate different contracts.
* Repeated invalid numeric values distinguish bool, nonfinite, nonpositive, huge-int conversion, domain type and range errors. They are cheap and not interchangeable with one arbitrary failing input. Paired extreme-positive and permitted alternative-layout cases remain.
* The unsupported ImageJ source test can fail at harmonize rather than exporter when that existing authoritative boundary rejects mode/mapping. The public contract explicitly permits the existing boundary; it is not evidence of a broken rejection oracle and is not marked F.
* Some raw permutation examples are equivalent examples under the same coordinate rule. Their title is not a proof of all120 SIM permutations, and no test count supplies universal correctness. They are small pure array calls; there is no measured reason here to reduce them.
* ImageJ report-limitations tests intentionally check representation and retain actual text for independent semantic review. Passing them does not certify English disclosure truth. Consolidation must not silently upgrade the claim or remove retained report observations.
* M25 and ImageJ resource tests prove different resource scopes and failure modes. The192MiB ImageJ payload,128MiB opaque extension, two block sizes, large real source-change race and genuine EFBIG child are not redundant with M25 and remain untouched.
* Hash/provenance memoization is not recommended without measured savings. Recomputing immutable-input evidence may be cheap enough; preserve provenance over marginal speculative work. If later profiling identifies it, any reuse needs its own exact-input/changed-input validation.
